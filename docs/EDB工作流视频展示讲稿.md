# EDB 地方经济数据工作流展示

## 一 开场与项目背景

【画面：展示 DC 整体工作流，先缩小到能看到完整链路。】

大家好，今天介绍的是我搭建的 EDB 地方经济数据处理工作流，以及其中接入的外部 Agent 服务。

这个工作流要解决的问题，是从政府网站发布的 Excel、html网页， PDF、图片等各种文件类型中，提取我们需要的经济指标，匹配指标编码，并数据清洗内审等环节最终输出json结构化结果，交给平台继续处理。

难点在于，不同文件内容格式差别很大。（同样是地区生产总值，有的表格需要合并行标题和列表头，才能确定完整指标名称；有的单位写在表头，有的写在括号里；统计期间也可能藏在标题或文件名中。）以前这些情况需要人工逐个分析，再编写解析代码。

所以我把这部分工作接入了 Agent：让它结合真实文件、指标规则和已有解析规范，生成解析代码或提示词，执行后再检查结果。同时，把通过检查的解析资产保存下来，方便后续复用，减少重复生成带来的 Token 成本。

## 二 整体工作流怎么运行

【画面：从开始节点，依次移动到规则查询、文件类型判断、三个 Agent 接入分支，再展示后处理链。】

先看整体流程。DC 收到一条数据后，会拿到来源路径、文件标识、标题、发布日期等信息。接着根据来源路径查询指标规则库，确定这次需要提取哪些指标、对应什么编码，以及标准单位和发布频率。

这里有一个关键变量叫 `pageTitle`。它表示来源栏目路径，比如某个政府网站下面的统计数据栏目。它主要用来定位规则和已有解析代码资产。

查询得到的规则放在 `GZKJG` 中。可以把它理解为本次提取任务的目标清单：我们要找什么指标，最后应该匹配到哪个编码。

之后，工作流根据文件类型进入 Excel、HTML 或 Prompt 分支。Excel 主要读取工作簿；HTML 主要处理转换后的网页正文；PDF、图片等资料在上游完成正文转换后，进入 Prompt 分支进行提取。

三个分支都接入同一个外部 Agent 服务，由服务侧完成解析、执行和匹配。结果通过检查后，再返回 DC，衔接原有的单位换算、数据清洗、内审和标注流程。


## 三 Agent 接入与任务查询

【画面：打开一个接入节点，展示入参映射；切换到脱敏后的 HTTP 请求或任务日志。】

接入节点通过 HTTP 调用 Agent。第一次使用 POST 提交任务，服务返回一个 `job_id`，也就是任务编号。后续使用 GET 查询这个任务的进度和结果。

这里之所以采用提交加查询，是因为生成和审核可能需要几分钟，而 DC 单次节点执行有时间限制。把任务放到外部服务后，即使本次查询结束，服务端也可以继续处理。

所以，看到 `queued` 或 `running`，表示任务还在排队或执行，需要继续查询同一个任务。只有状态变为 `ready`，才进入结果接出。`failed` 或 `interrupted` 则需要结合具体错误处理。

重试时要保持同一个 `job_id`；如果提交超时、还没拿到任务编号，也要保持本次输入和 `workflow_run_id` 一致，避免反复创建重复任务。

## 四 Agent 内部具体做什么

【画面：切到 Agent 项目目录或准备好的流程说明，按下面四步讲解。】

接下来重点介绍 Agent 内部。我把它分成四个环节：已有资产查找、生成前检查、解析与审核，以及结果交付。

### 1 先查已有解析资产

Agent 拿到 `pageTitle` 后，会先把路径中的正斜杠和反斜杠转成下划线，按同名文件查找已有的解析代码或提示词。

比如，同一个统计栏目以前已经写过正确的解析代码，下个月又来了新文件，就可以复用这段代码，解析本次文件，再进行指标匹配和结果检查。复用的是解析方法，本期的数值和统计日期仍然需要重新读取。

对于我明确指定的已有代码库，命中 Python 代码后，会执行一次并进入匹配，不再调用模型生成代码，也不进入自动重建循环。执行失败就返回具体原因。

Prompt 分支复用的是提示词，所以可以省去提示词生成，但提取本次正文时仍然需要调用模型。

另外，Agent 自己生成并通过检查的资产也会按 Excel、HTML、Prompt 分类保存。自动缓存会结合规则和 Skill 等条件判断能否复用，避免规则已经变了，却仍然直接套用旧代码。

这一部分能够减少重复生成代码或提示词产生的 Token 消耗，尤其适合同一栏目持续发布月报、季报的场景。

### 2 生成前先检查任务是否值得继续

如果没有可用的已有资产，才进入生成流程。

首先检查 `GZKJG` 是否有效。如果没有指标规则，就直接返回“指标规则为空或无效”，不调用 DeepSeek。因为目标都没有确定，继续生成也无法完成正确匹配。

接着下载并读取真实源文件，再让 DeepSeek 做内容预审：文件里是否有有效业务数据，这些内容是否与本次规则相关。

如果明确没有数据，或者与目标指标完全不相关，就提前结束并说明原因。证据不足时，不能直接判断无数据。这一步也能避免把模型调用浪费在明显无法完成的任务上。

### 3 按规范生成 再执行和审核

这里的 Skill，可以理解为整理好的解析操作规范。它把长期积累的处理方法写清楚，例如怎样理解合并表头、怎样拼接指标名称、怎样寻找单位和统计期间，以及输出应该遵守什么格式。

DeepSeek 会结合这些规范、可用的名称规则和真实源内容，生成完整解析代码或提示词。比如一个表格里，行标题是“地区生产总值”，列标题是“累计值”，就需要结合上下文确定它的完整含义，不能只看某一个单元格。

生成之后必须实际执行，再检查提取结果。这里主要看三个方面。

第一，是否提取到了有效明细。源文件有数据，但提取为空，就需要结合源文件和错误信息修复。

第二，统计期间是否有依据。`end_date` 表示数据统计到哪一天；`publictime` 表示文章什么时候发布。比如六月的数据在七月发布，统计截止日仍然是六月三十日，不能拿发布日期代替。

第三，指标匹配是否正确。Agent 会将提取出的名称与 `GZKJG` 对照，在生成流程中结合源文证据检查名称和含义。累计值、当期值、同比增速，以及总项和子项，都需要区分，不能只因为名称相近就强行匹配。

如果检查未通过，生成流程允许根据反馈修复：初次生成加最多两次重建，总共最多三次。超过上限仍未通过，就返回失败原因，留给人工定位，避免无限循环消耗模型额度。

### 4 保存证据并交付结果

通过检查后，Agent 会保存解析资产、执行结果和必要的审核记录，再把结果交给 DC。

如果失败，也会保留源文件和失败任务记录。我们可以通过 `job_id` 查看失败阶段、错误码和中文原因，例如规则为空、提取为空，或者无法确定统计截止日期。

这些记录便于排查问题。失败记录本身不会自动触发历史任务重跑。

## 五 用一个成功结果讲清楚输出

【画面：展示已有的成功任务结果，展开 excel_data 和 OUTDATA。不要在录制时直接展示令牌或模型密钥。】

这里用滕州市财政简报这个已有成功案例说明输出。

`excel_data` 保存的是解析后的原始业务明细。虽然名字里带有 Excel，目前 Excel 和 HTML 分支都可以返回它。每条数据包括指标名称、数值、源单位和统计截止日期。

例如，“一般公共预算收入累计值”提取为 48.82，源单位是亿元，统计截止日期是 2026 年 6 月 30 日。

与规则库匹配后，数据会增加对应的指标编码，再交给后续单位换算链处理。这个指标的标准单位如果是万元，就按照一亿元等于一万万元，换算为 488200 万元。

所以，`excel_data` 主要帮助我们检查原文提取是否正确；`OUTDATA` 是匹配后的结构化结果，DC 接出后通常映射到 `out_data`，再继续清洗和换算。判断数值是否正确，需要同时看当前处理阶段和单位。

`unitArray` 则用来整理源单位、标准单位和换算比例，给下游单位处理提供信息。

这里还会返回 `PythonCode`、`PythonFile`，或者 Prompt 分支的 `PromptCode`、`PromptFile`，分别表示解析资产内容和文件标识。DC 接出时会校验资产哈希，确认传输内容完整；哈希校验之后，还要继续遵守业务结果的检查规则。

Prompt 分支的核心业务输出是 `OUTDATA`，不要求它一定带有 `excel_data`，这一点和 Excel、HTML 分支有所不同。

## 六 后处理与项目价值

【画面：回到 DC，展示成功判断之后的单位换算、清洗、内审和标注节点。】

Agent 返回结果后，DC 继续执行原有后处理链。包括根据标准单位换算数值、按平台要求清洗字段，以及检查统计期间、指标频率和业务数据，最后进入相应的内审与标注环节。

这套项目的核心，是把文件解析从逐个手工处理，变成一个能够复用资产、实际执行、检查结果，并在限定次数内修复的处理过程。

对我来说，最有价值的两个部分，一是让不同格式文件统一接入原有业务流程；二是让已经生成成功的解析代码和提示词可以持续复用，减少后续重复工作和模型生成成本。

以上就是这个工作流的整体介绍。

## 变量速查

录制时优先讲 pageTitle、GZKJG、job_id、excel_data、OUTDATA、end_date 六个变量。其他字段只在对应画面出现时补充，避免逐项念接口文档。

### 输入与规则

| 变量 | 含义及作用 | 讲解提醒 |
| --- | --- | --- |
| `pageTitle` | 来源栏目路径，用来定位规则和解析资产 | 同栏目可有多期文件，不是单个文件的唯一标识 |
| `title` | 本次资料标题，辅助理解主题和统计期间 | 与栏目路径区分；不能无证据推断日期 |
| `fileType` | 真实文件类型，例如 xlsx、html、pdf、png | 由它选择解析策略，不要为了走分支伪造类型 |
| `fileMd5` | 本次源文件在文件库中的标识 | 路径相同仍要读取本期文件 |
| `markdownMD5` | 上游转换后的正文标识，供 HTML、Prompt 等分支使用 | Agent 此接口不负责直接完成图片 OCR |
| `GZKJG` | 本次指标规则列表，常位于 `GZK.GZKJG` 中 | 目标指标清单，不是提取出的数据 |
| `rule_indicator_code` | 规则中的指标编码 | 最终结果用它关联标准指标 |
| `rule_indicator_name` | 规则中的目标指标名称 | 名称相似仍要确认统计含义 |
| `rule_constant_name` | 规则中的标准单位 | 不等于源文件的实际单位 |
| `indicator_release_frequency` | 指标发布频率，如月、季、年 | 与统计期间和后续内审相关 |
| `data_target_table` | 数据应进入的目标表 | 地方经济过滤脚本使用 `usrDFJJYXSJB` 作为允许目标表 |

### 任务状态与接口

| 变量 | 含义及作用 | 讲解提醒 |
| --- | --- | --- |
| `workflow_run_id` | 本次工作流运行标识，参与防重复受理 | 同一次提交超时重试应保持一致 |
| `job_id` | Agent 任务编号，供查询和定位日志 | 等待中查询同一编号，不反复新建任务 |
| `parse_strategy` | 实际解析策略：excel、html、prompt | 策略名称不等于源文件扩展名 |
| `status` | queued 排队；running 执行；ready 可交付；failed 失败；interrupted 中断 | queued、running 不能按成功结果接出 |
| `stage` | 当前处理或失败阶段 | 帮助区分提交、规则查询、执行等问题 |
| `error_code` 与 `message` | 错误类别和中文原因 | 用具体原因排查，不能把所有超时归因于模型 |
| `SERVICE_BASE_URL` | DC 调用的 Agent 服务地址 | 必须从 DC 所在环境实际可达 |
| `NODE_WAIT_SECONDS` | 接入脚本本次等待预算 | 不等于服务端任务总耗时上限 |

### 结果与解析资产

| 变量 | 含义及作用 | 讲解提醒 |
| --- | --- | --- |
| `ExcelData` / `excel_data` | 解析器常用的提取明细字段，以及交付给 DC 的明细字段 | 大小写和字段映射需要按实际节点契约对齐 |
| `indicator_name`、`indicator_data`、`indicator_unit` | 指标名称、数值和源单位 | 生成解析时保留真实源数值与单位 |
| `end_date` | 数据统计截止日期 | 不能用 publictime 补空 |
| `publictime` | 资料信息发布日期 | 可能晚于统计期 |
| `OUTDATA` / `out_data` | 匹配后的业务结果与 DC 常用接出字段 | 是否完成单位换算，要看所处节点 |
| `unitArray` | 源单位、标准单位和换算比例的整理结果 | Prompt 接出可按原 MD 链适配，不能假定与表格分支完全相同 |
| `KB_unit`、`convert_ratio` | 标准单位、单位换算比例 | 比例应来自平台认可的换算规则 |
| `PythonCode`、`PythonFile` | Python 解析代码内容、文件标识 | Excel、HTML 常用；已有代码执行仍需本次源文件 |
| `PromptCode`、`PromptFile` | 提取提示词内容、文件标识 | 复用提示词后，提取步骤仍调用模型 |
| `result_json` | DC 适配层承载的业务结果 JSON 字符串 | HTTP 的 result 与 DC 的 result_json 是不同包装层 |
| `code_sha256` | 交付资产内容的完整性摘要 | 证明内容一致，不证明业务语义一定正确 |
| `cache_hit` | 是否命中相应缓存 | 不能据此认定本期数据无需检查 |
| `parser_params` | 传给解析器 main 函数的输入字典 | 删除路由代码字段后传入；返回值由解析器 main 决定，它本身不是 ExcelData |

## 可按需要插入的补充讲解

### 为什么要区分 Skill 和缓存

“Skill 保存的是解析方法和约束，缓存保存的是已经生成过的代码或提示词。没有资产时，模型参考 Skill 生成；有合适资产时，就优先复用。运行过程中保留的错误和审核记录，也可以作为后续人工完善规范的依据。”

### 为什么有了匹配还需要审核

“匹配解决的是名称与编码的对应关系，审核还要确认源文含义。比如同比增长和累计值可能出现在相邻列，单看名称命中并不能证明数值取对了，所以还需要检查真实表头、单位和统计期间。”

### 为什么查询超时还要继续查同一个任务

“DC 这一次没有等到结果，不代表服务端已经停止。只要任务还在 running，就继续查询同一个 job_id。终止失败需要修复具体原因，不能把所有失败都做成无限重试。”

### 地方经济目标表过滤怎么讲

“在入口增加目标表判断，只允许地方经济目标表的数据继续，其他目标表正常跳过。缺失或冲突的目标表也先停止，避免把其他业务的数据送入这条链路。”

录制前确认这个节点和条件分支已经在 DC 中接好。当前本机已有过滤脚本，只有完成平台接线后，才能在视频中演示为已生效功能。

## 录制前准备

1. 准备三处画面：DC 全流程、Agent 任务处理日志、一个已成功任务的输入和输出。主案例选一个熟悉的成功任务，避免现场等待完整生成。
2. 展示输入时突出 pageTitle、GZKJG 和源文件标识；展示输出时并排看 excel_data 与匹配结果，核对源文件中的对应数据。
3. 介绍已有资产复用时，展示路径转文件名和命中文件，再展示本期执行结果。不要把历史数据直接当作本次结果。
4. 隐藏 SERVICE_TOKEN、模型 Key、内部接口地址和不宜公开的源资料。若视频对外发布，使用脱敏截图或合成输入。
5. 原方案 47 个节点、新方案 45 个节点的数量来自此前工作流快照。如需口播，先确认录制时平台版本；后续新增过滤节点后，数量可能变化。
6. 不直接宣称节省了某个百分比的 Token 或提升了某个准确率，除非已有对比统计。可以准确地说“减少重复生成调用和对应 Token 消耗”。
